01 Summary / abstract

A budgeting app built for the AI world we now live in

The goal was to rethink budgeting around something people increasingly understand: communicating with an AI agent. Instead of making users navigate a rigid ledger, the product uses familiar, conversational interactions to help categorize spending, maintain envelopes, and make routine decisions on the user's behalf.

The ambition was not to automate the user out of budgeting. It was to automate the repetitive work without separating the user from each individual purchase. Every transaction still creates a brief moment of recognition: what was bought, how much it cost, and where it belongs.

That interaction matters because awareness is not only about the total amount spent. It is also about the sheer number of purchases being made. A short confirmation for each charge keeps the user grounded in both dimensions while AI handles merchant cleanup, recommendations, and the mechanics of updating the budget.

Defining product principle
Automate the work of budgeting, not the awareness that makes budgeting valuable.

03 The important shift

From asking AI for answers to asking AI for better questions

The quality of the product improved when the AI stopped behaving like a rapid solution generator and began behaving like a discovery partner. A two-to-three-round interview created space to challenge assumptions, expose dependencies, and turn instinctive “what if” ideas into product decisions.

The prompt became part of the product process. It established roles, phases, decision gates, technical constraints, verification expectations, and clear instructions to pause for clarification. That scaffolding made the AI's broader knowledge available without surrendering product judgment.

05 What I learned

The lessons extended beyond one budgeting app

This project changed how I think about prototypes, prompting, and the relationship between product vision and technical foundations.

  1. A professional prototype is an ecosystem, not a single application

    I learned that numerous applications and tools are necessary to create more professionally constructed prototypes for web-based products. The interface is only one layer. Runtimes, package managers, an API, a database, source control, formatting, compilation, and browser validation all contribute to whether a prototype is credible and repeatable.

  2. Product vision improves when AI is required to clarify

    I learned the importance of iterating on a product vision with AI and explicitly requiring it to ask clarifying questions rather than jump straight to a conclusion. A simplistic prototype can move only as fast as my own “what if it did this?” creativity. A structured dialogue uses AI's much broader ability to ask “what if?” and “how do you envision this working?” while leaving the final decisions with me.

  3. Backend thinking turns a story into a system

    I learned the importance of thinking through how information will be stored, related, changed, and retrieved. Frontend work is powerful for storytelling, but a well-considered backend and database allow the prototype to retain state, support richer behavior, integrate with larger systems, and evolve into something that can be demonstrated repeatedly and scaled responsibly.

  4. Verification is part of prototyping

    I learned that “it looks right” is not the same as “it works.” Building the complete path from screen to API to database, then testing save, reload, CORS, and responsive layouts, created evidence that the concept was more than a visual mockup.

  5. Moving a project folder is not a neutral operation

    I relocated the whole prototype to its own folder to keep it separate from a much larger, unrelated backend repository. That single move broke the frontend: pnpm had installed dependencies as Windows junctions with absolute paths baked in, and once the original folder was gone, every import silently pointed at nothing. Nothing in the application code was wrong; the environment underneath it was. The fix was a clean reinstall of dependencies from the new location, and the lesson was broader than pnpm — a working prototype depends on an environment, not just a codebase, and that environment does not always travel with a simple copy or move.

08 Prototyping and iterating

The interview habit didn't stop once the prototype was running

Real use against the live app turned up a bug and, separately, a feature idea. Both moved through the same discipline established during product discovery: describe the problem in plain language, let the AI ask clarifying questions before touching any code, then verify the result in the running app rather than trusting the description of it.

Propose / report

"The login button is stuck"

Reported that neither a teammate's account nor any other login could get past a permanently "logging in…" button, then separately asked for a friendlier, more capable allocation step inside onboarding.

Outcome: two concrete asks
Clarify

Questions before code

Before redesigning the allocation step, seven clarifying questions were asked and answered: where the sticky elements should live, whether the slider should ever overwrite typed dollar amounts, which gauge style to reuse, what the mobile fallback should be, and how over-budget warnings should behave.

Outcome: a shared, specific spec
Implement & verify

Fixed, built, and proven live

The login bug traced to one state value defaulting to "loading" before any attempt was made. The allocation step became a draggable three-way slider, three live per-group gauges, a sticky total-allocated tracker, and split Needs / Wants / Savings tables — confirmed in the running app at desktop and mobile widths.
