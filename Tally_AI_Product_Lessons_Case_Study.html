The starting problem

Tally already has a working feature called Transaction Review: it groups a user's uncategorized transactions by suggested envelope (Dining, Transportation, Dates, etc.), lets the user approve or remove each suggestion, and optionally teach Tally to always suggest a category for a given vendor in the future. The user experience was fully designed and built.

The problem was underneath it: the "suggestion" came from a hardcoded list of keywords ("coffee" → Dining, "gas" → Transportation) with made-up confidence numbers that didn't measure anything real. It was the same for every user, forever, and never got better. This case study walks through how that gets replaced with something that actually learns from each user's real behavior — and, along the way, surfaces the handful of questions that come up in any product trying to add a genuine AI-assisted feature, not just this one.

The myth to drop first: "training an AI"

Most people hear "AI feature" and picture something that requires enormous datasets, GPUs, and weeks of machine learning engineering — adjusting a model's internal numbers (its weights) through training. None of that happens here.

Instead, this uses a technique called Retrieval-Augmented Generation (RAG): a general-purpose pretrained model (OpenAI's GPT) never changes at all. What changes, request by request, is the evidence handed to it in the prompt — the user's own history, growing richer over time. The model supplies general reasoning ability; your own code supplies the facts that matter for this specific decision.

flowchart LR subgraph Fixed["Stays exactly the same, forever"] M(("OpenAI GPT model")) end subgraph Growing["Grows richer over time"] E1["Week 1: almost no evidence"] E2["Month 3: real history + early corrections"] E3["Month 12: hundreds of confirmed events"] end E1 -->|prompt| M --> R1["Weak, generic suggestion"] E2 -->|prompt| M --> R2["Better, more specific suggestion"] E3 -->|prompt| M --> R3["Strong, personalized suggestion"]

"Tally gets smarter over time" means the evidence store grows — not that any model gets retrained.

The seven recurring questions

Every product that adds a real AI-assisted recommendation feature ends up answering the same handful of questions, in roughly this order. Tally's transaction categorization feature is the worked example for each one.

Question 1

What is the model's job, precisely?

A vague instruction ("categorize this transaction") invites the model to guess at things it can't actually know. A narrow, explicit instruction keeps it honest.

Applied to Tally "Select the existing envelope best supported by this user's confirmed history and definitions. Treat rejected suggestions as negative evidence. Do not invent purchase purpose. Request input when the evidence cannot distinguish plausible destinations." That middle sentence matters — the model should never claim to know why someone bought something beyond what the evidence actually shows.
Question 2

Where does trustworthy evidence come from?

You don't hand a model a user's entire history and hope it finds the relevant part — you retrieve just the slice that matters for this decision: same-vendor history first, then comparable purchases, then explicit rules.

Applied to Tally A new append-only log (categorization_events) records every confirmed categorization, rejection, and correction, scoped per user. Retrieval means a simple filtered query — "give me this user's history for this exact vendor" — not a search across everyone's data.
Question 3

How do you turn raw evidence into something interpretable?

This is classic feature engineering — computing a handful of countable, explainable summaries instead of asking the model to eyeball a pile of raw rows.

Applied to Tally Instead of "mostly Dates," the signal is "6 confirmed Dates, 2 confirmed Dining, last 3 were Dates, 1 historical rejection on record." Keeping exceptions visible (not smoothing them away) is what lets the model — or a deterministic rule — reason about genuine ambiguity.
Question 4

When do you trust a recommendation vs. defer to a human?

Sometimes called trust calibration or selective prediction. Every confidence threshold trades precision (how often it's right when it speaks up) against recall / coverage (how often it speaks up at all) — raising the bar makes it righter but quieter; lowering it makes it chattier but less trustworthy.

Applied to Tally There's no single AI gate — there's a cascade: (1) an explicit vendor rule always wins outright; (2) if the pipeline's own evidence-based confidence (not the model's self-reported number) is extremely high, skip the model entirely and suggest directly; (3) only genuinely ambiguous or thin-evidence cases are escalated to an actual model call.

Question 5

How do you stop a bad or hallucinated output from causing damage?

Two separate checks, often conflated: is the response well-formed and real (structural validation), and separately, is the response well-supported enough to act on (the threshold question from Question 4). A model can pass the first check and still be a weak guess.

Applied to Tally Never trust a model-returned envelope ID just because it looks plausible — check it against the real list you actually sent it. Likewise, if the model cites specific evidence to justify its answer, verify that evidence actually existed in what was sent — a model can write a confident-sounding explanation that isn't actually grounded in anything real, sometimes called hallucinated grounding.
Question 6

How does it improve over time without retraining anything?

Every user decision — approve, reject, correct, create a rule — becomes one more row of evidence for the next decision. The model stays fixed; only what it's shown grows.

Applied to Tally Approving a suggestion confirms it. Removing one is recorded as a real rejection — a permanent negative signal, not something that "expires." This is what makes next month's suggestion for the same vendor better than this month's, with zero model retraining involved.
Question 7

How do you know any of this is actually working?

Not by intuition — by replaying real, labeled history through the pipeline and measuring it, carefully avoiding look-ahead bias (letting the evaluation "see" data from after the point it's supposedly predicting, which quietly inflates how good a system looks).

Applied to Tally Two years of one household's real spending history becomes a development/testing asset: walk through it chronologically, pretend you can only see what existed before each transaction, and check whether the pipeline would have gotten it right. This is exactly where real precision/recall numbers (Question 4's table) come from — not a guess.
A trap worth naming One household's real data proves the mechanism works on genuinely messy real-world data — it does not prove the system generalizes to every user's different envelope setup. Treating one person's data as "the template everyone should match" is a classic mistake called overfitting — tuning so precisely to one example that it fails to generalize. Real confidence about generalization only comes from many different real users, over time.

Vocabulary glossary

Retrieval-Augmented Generation (RAG)
Feeding a fixed, pretrained model relevant facts at request time instead of training it on your data.
Cold start
The problem of having no history yet for a brand-new user or item, so a personalization system has nothing to retrieve.
Feature engineering
Turning raw data into the handful of countable, meaningful summaries a decision actually depends on.
Precision
Of the cases where a system spoke up confidently, how often was it actually right?
Recall / coverage
Of all the cases that existed, how many did the system confidently handle at all (vs. deferring)?
Trust calibration / selective prediction
Deciding when a system should act/recommend confidently versus defer to a human.
Hallucinated grounding
When a model's explanation sounds evidence-based but cites or implies facts that weren't actually supplied to it.
Look-ahead bias / data leakage
Accidentally letting an evaluation "see" information from after the point it's supposed to be predicting, which makes a system look better than it really is.
Overfitting
Tuning a system so precisely to one specific dataset/example that it fails to generalize to new, different cases.
Multi-tenancy (row-level scoping)
Many users' data living in one shared table/schema, isolated only by always filtering queries by an owner column — not by separate databases per user.
Cascade / tiered architecture
Cheap, deterministic logic resolves the easy majority of cases; an expensive model is reserved only for genuinely ambiguous ones.
