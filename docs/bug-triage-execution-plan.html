AI Bug Triage Pipeline — Execution Plan

Status: Rebuild in progress Author: Jeff Riney Last updated: 2026-09-19
This document is the current source of truth for phases, build order, and per-phase inputs/tools/outputs. Treat it as living — update it as decisions change.

Why We're Doing This

The problem

Triaging firmware and backend software bug JIRA tickets is slow and inconsistent today: an engineer has to manually find the customer's CID, log into Partner Portal, pull diagnostic logs, reason about firmware behavior, cross-check that reasoning against the FALCOR backend codebase, pull relevant event history, and write up a coherent summary — all before anyone can even start fixing the actual bug.

Why it's automatable

Every piece of this already has a working building block available: a JIRA MCP integration for reading/writing tickets, browser/Playwright automation for Partner Portal (login already validated end-to-end against a real test CID), a local checkout of the FALCOR backend for code cross-referencing, and AI reasoning for the judgment-call steps. This is assembly, not new capability.

Desired outcome

A flagged JIRA bug ticket automatically gets its CID's logs pulled from Partner Portal, analyzed against firmware behavior and the FALCOR backend codebase plus event history, and ends up with a detailed, evidence-cited draft report — reducing manual triage from hours to minutes, while a human still approves anything that posts back to JIRA or triggers a real device action.

What Changed

The prior architecture was a fully AI-agent-driven pipeline — a chain of four chat-native custom agents (Orchestrator → Portal Log Collector → Firmware Log Triage → Bug Triage Synthesizer) that handled everything, including the mechanical Partner Portal steps, inside interactive AI sessions.

This rebuild splits the pipeline explicitly by who/what performs each step, and reorders the build so the deterministic, lowest-risk plumbing gets built and proven first:

  • Steps that are mechanical, repeatable, and security-sensitive (portal login, log/event-history retrieval) are deterministic Python/Playwright scripts — no AI judgment involved, no AI ever sees credentials.
  • Steps that are genuinely judgment calls (parsing logs into findings, cross-referencing against the backend and event history, drafting a summary) stay AI-driven.
  • Posting the final summary to JIRA is its own explicit phase, separated from the analysis that produces it.
  • JIRA ticket-intake/watching (previously implicit in the Orchestrator) is now its own phase — and deliberately the lowest priority, built last, since manual per-ticket triggering is good enough for now.

Phase 1 Operational Model (Non-AI Runner)

Phase 1 is intentionally deterministic and can be executed by a normal script runner (for example, a local shell session, Task Scheduler, or another non-AI orchestrator). No AI layer is required for portal authentication.

How authentication works

  • Credentials are loaded from local environment configuration: PORTAL_URL, PORTAL_USERNAME, PORTAL_PASSWORD, and PORTAL_TOKEN.
  • PORTAL_TOKEN is the remembered-device value (twoFactorAuthenticationId) harvested once by a human from a successful login where "remember this device" is checked.
  • The login script injects this token before credential submit so normal runs bypass the interactive email 2FA prompt.
  • This is a trusted-device reuse mechanism, not permanent 2FA removal; token expiry still requires manual refresh.

Deterministic run sequence

  1. Run scripts/login.py as the first gate for any portal workflow.
  2. Parse the single JSON status line from stdout and branch behavior by status.
  3. On success, proceed to Phase 2 scripts (CID navigation, log/event-history retrieval).
  4. On 2fa-required, stop immediately and require human token re-harvest.
  5. On login-failed, stop and alert for credential or portal-state investigation.

Operational guardrails for unattended execution

  • Use least-privilege file access for local secret material (.env, auth_state.json).
  • Never print or persist secret values in logs; only emit status-level outcomes.
  • Keep secrets and downloaded artifacts gitignored; do not commit them under any circumstance.
  • Treat 2fa-required as a hard stop condition in scheduler jobs (no blind retries).

Phase 2 Operational Model (Non-AI Runner)

Phase 2 is now implemented as a deterministic Playwright flow and can be run by a normal script runner. It does not require AI decision-making to navigate the portal and trigger log download.

Implemented deliverable (logs path)

  • Primary script is playwright/recordings/phase2-portal-flow.spec.ts.
  • Flow includes Home → Find Customer → CID search → Command Catalog → AirFx legacy toolkit → Upload Panel Logs (Internal) → Bulk Download.
  • A deterministic refresh gate is included: 5 consecutive page refreshes, each spaced by 60 seconds, before upload/download actions continue.

Artifact contract for Phase 3

  • Downloaded file is explicitly saved into workspace artifacts (not temp browser storage).
  • Per-run output folder: artifacts/partner-portal/runs/<runId>/.
  • Per-run manifest: artifacts/partner-portal/runs/<runId>/manifest.json containing CID, phase, timestamp, and saved file path.
  • Latest pointer file: artifacts/partner-portal/latest-run.json for Phase 3 "read latest" behavior.

Current scope limits

  • Logs export path is implemented and validated.
  • Event-history export path is not implemented yet in the current deterministic runner.
  • The prior Python Phase 2 export script (scripts/download_export.py) was intentionally removed; current source of truth is the Playwright Phase 2 spec above.

Phase 3 Operational Model (Non-AI Runner)

Phase 3 turned out to be fully deterministic once the log format was inspected against two real CID samples — no AI judgment is needed to reshape raw exports into a structured, queryable format. AI only enters at Phase 4, which reads this output rather than the raw archives.

Implemented deliverable

  • Script is phase3-log-parsing/phase3_parse_logs.py — pure Python standard library (gzip, tarfile, re, json, argparse); no external dependencies, no network calls.
  • Accepts either a still-compressed Phase 2 run folder (Combined_AEL_Logs*.gz + climax_logs.tgz) or an already-extracted copy of the same tree — auto-detected.
  • Normalizes four distinct log families, each verified against real byte-level samples rather than assumed: AEL text logs, Climax JSON config snapshots, an 11-field NUL-delimited tabular log family (debug*.log, system.log, alarm.log), and a separate RX/TX communication-trace format (adcapp_debug*.log, usdk_debug*.log).
  • Validated end-to-end against two real CID log pulls (CID 17803772 and CID 20954439 / CMX-6300), including a spot-check confirming it correctly captures the exact LED brightness/state log lines behind a real, already-fixed bug.

Output contract for Phase 4

  • Per-run output folder: parsed-logs/<run-folder-name>/.
  • parsed-logs.jsonl — one normalized JSON record per line, tagged by source (ael, config, climax_log, climax_comm_log).
  • AEL records carry an eid (nullable numeric event id) and a message_template (message text with variable numbers replaced by #) — deliberate, deterministic correlation keys so Phase 4 can grep the HxGW2 firmware repo for an exact EID::e<n> call site or a literal os_printf_d/os_printf_w format string, instead of fuzzy-matching text.
  • summary.json — record counts per family plus input/output paths, mirroring Phase 2's manifest.json convention.

Current scope limits

  • Not yet wired to real Phase 2 output — validated only against manually supplied sample folders, since no artifacts/partner-portal/ folder exists in the workspace yet. Testing this connection is the immediate next step.
  • The 8 unlabeled positional fields in the climax_log tabular family have undocumented semantic meaning — kept positional rather than guessed; may need firmware source cross-referencing later if Phase 4 needs them.
  • Timestamp/timezone normalization across log families is intentionally deferred — raw timestamp strings are preserved as-is.
  • Event-history export (from Phase 2) is not yet consumed by this parser — Phase 2 hasn't implemented that export path yet either.

Phase 4 Solution: Independent Search + Synthesis Automated / AI

Phase 4 uses three independent searches run with no cross-talk — HxGW2 (firmware), Alarm-backend (FALCOR), and the Climax XML protocol document — each producing its own cited findings and a per-repository confidence level, followed by a synthesis stage that cross-compares all three before producing the final report. Validated live end-to-end against a real ticket (CMX-6300) with a real, already-merged fix commit as ground truth.

Implemented deliverable

  • phase4-log-triage/build_phase4_input.py — deterministic (stdlib only) input builder. Slices Phase 3's parsed-logs.jsonl to the ticket's time window, checks which knowledge bases actually exist on disk, and writes one phase4-input.json manifest + a window-slice.jsonl — the only things the AI legs ever see, never the raw multi-million-line logs or a hand-pasted ticket.
  • .github/agents/phase4-hxgw2-search.agent.md, phase4-backend-search.agent.md, phase4-climax-xml-search.agent.md — three independent search subagents, each scoped to exactly one knowledge base, each running a two-step search (log/EID-anchored, then concept-keyword) plus a version-control ground-truth check when the target is a git repo.
  • .github/agents/phase4-synthesizer.agent.md — cross-compares the three leg outputs, extracts a shared identifier list to trace across repos, checks version control for a ticket-referencing fix commit, optionally runs one bounded secondary search, and produces the final report.
  • .github/agents/phase4-orchestrator.agent.md — sequences the pipeline end-to-end.

Output contract

  • Final report shape: problem restatement, RCA summary, areas searched, confidence per repository (HxGW2 / Alarm-backend / Climax XML — low | medium | high | not_available), and a call to action for potential code fixes.
  • The Climax XML leg fails safe: if sources.climax_xml.available is false in the manifest, it reports status: source_unavailable rather than fabricating from training knowledge — this is the current state, since the Climax XML document hasn't been converted into a machine-readable form in this workspace yet.

Validated against CMX-6300 (real ticket, real ground truth)

  • Ran the real ticket ("Flashing yellow LED #3 even though the panel is communicating over cellular") through the HxGW2 and Alarm-backend legs plus synthesis. The HxGW2 leg's log/EID-anchored search independently landed on send_3LedPatternCommands() in CiAel_Hxgw.cc — the exact function later confirmed (via git history) to contain the real fix.
  • Confirmed via git log --all --grep="CMX-6300" inside the adc_embedded_linux submodule that commit 179e4c861c ("fixed the connectivity recovery pattern matching to ignore the brightness") is the real fix, and git merge-base --is-ancestor confirmed it's already merged into the checked-out HEAD — i.e. the code searched was already post-fix.
  • Calibration lesson learned and now baked into the agents: a follow-up hypothesis built by pattern-matching a plausible-sounding description (without checking the diff) was a red herring — a different function that also compares LED brightness/state but wasn't what the real commit touched. Version control, when available, must override a hypothesis that only "sounds right."

Current scope limits

  • Climax XML leg is untested for real — the source document (AlarmDotCom XML command.doc, confirmed by the user to be the Climax XML piece) is a legacy binary Word format; conversion attempts (Word COM automation, raw byte extraction) haven't yet produced a clean machine-readable copy. Once a text/HTML version is available, wire its path into --climax-xml-path.
  • Not yet wired to a real Phase 2 run's output — tested against the manually supplied _cmx6300-extract/ sample, same caveat as Phase 3.
  • Only validated on one ticket so far — still needs workshopping against more real tickets with known, merged fix commits as ground truth before treating this design as proven.
