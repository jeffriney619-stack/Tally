01 / The distinction

Two documents, two different jobs

The Word document names the technologies and broad architecture. The kickoff prompt converts those choices into repeatable instructions that an AI agent can execute and verify.

The tech stack

What will be used

React, TypeScript, C#, SQL Server, tests, automation, and separate frontend and backend repositories. It is a blueprint of the major building materials.

The kickoff prompt

How it will be built

Installation, architecture, folder boundaries, conventions, verification gates, documentation, and handoff. It is the repeatable construction and inspection process.

Why the distinction matters

“Use React and C#” leaves hundreds of decisions unresolved. The prompt removes ambiguity about where code belongs, how services communicate, what counts as complete, and how future AI sessions should continue the work.

02 / The actual product

This is an operational system, not merely a website

The application must collect evidence, enforce rules, preserve history, and produce formal output. That is a much larger responsibility than displaying information on web pages.

01Import or manually enter equipment
02Create an inspection and test each device
03Record pass, fail, reasons, and corrections
04Finalize and generate the inspection report

The full system also needs authentication, dealer and account permissions, durable records, validation, audit history, report storage, deployment, and recovery from errors. That is why a full-stack architecture was selected instead of a spreadsheet, static page, or quick prototype.

Important: technology does not create regulatory compliance

A well-tested PDF is not automatically a compliant inspection report. Compliance depends on the applicable jurisdiction, Authority Having Jurisdiction, NFPA standard and edition, local amendments, required fields, testing frequency, licensing, signatures, retention, and correction rules. Those must be captured as product requirements and reviewed by qualified domain experts.

04 / How it likely evolved

The prompt reads like accumulated experience

Its language suggests your coworker worked backward from problems encountered while creating a real AI-assisted production application.

  1. AI behavior drifted between sessions. Repository-level Copilot instructions were added to preserve decisions after chat context disappeared.
  2. Setup failed on missing tools. Phase 0A was added to detect dependencies, explain them, request approval, install them, and verify them.
  3. Vague requirements caused invention. Phase 0B forces an interview about users, entities, relationships, and the first workflow.
  4. Frontend and backend work became disconnected. The prompt requires one vertical slice that crosses database, API, interface, and tests.
  5. Local database setup was fragile. Aspire became the one-command path for database, migrations, and API startup.
  6. Database models risked drifting. SQL scripts were declared the sole schema authority, with EF entities written to match.
  7. UI implementation became inconsistent. Styling, breakpoints, visible text, and network calls were each constrained to predictable patterns.
  8. Generated files looked finished without working. Every phase received a build, test, or live behavior gate.

The result is best understood as a collection of guardrails based on observed failure modes, not simply a fashionable list of libraries.

05 / Removing the prompt

The stack would still work, but the outcome would be less predictable

A developer can use React, C#, and SQL Server without this prompt. The prompt is not a technical prerequisite. It is a consistency and quality mechanism.

  • Frontend and backend might be placed in a different repository structure.
  • Minimal APIs might replace the requested controller structure.
  • EF migrations might replace the SQL source of truth.
  • Database entities might be exposed directly through the API.
  • Network calls might be scattered through UI components.
  • Authentication might be postponed until late development.
  • Visible English text might be hard-coded everywhere.
  • Responsive behavior and mobile tests might be skipped.
  • The database might be mocked instead of testing real persistence.
  • Generated code might never be compiled or started.
  • Later AI sessions might introduce conflicting patterns.
  • Missing installations might be left for you to diagnose.

Not every alternative is wrong

A monorepo, minimal APIs, or EF migrations can all be valid choices. The risk is not merely choosing a different tool. It is allowing choices to emerge accidentally, conflict with one another, or change from session to session without an explicit reason.

06 / Reusable minimum

Reuse the operating method, not necessarily the exact stack

  1. Describe the domain: identify users, their problem, core entities, relationships, and important rules.
  2. Select one vertical slice: build one small behavior completely from persistence through the user experience.
  3. Define boundaries: state where business logic, database access, API contracts, UI state, and visible text belong.
  4. Create simple startup: reduce undocumented local configuration and manual dependency ordering.
  5. Name each source of truth: define what governs behavior, database schema, contracts, and product requirements.
  6. Add automated gates: compile, type-check, lint, test, and exercise a real user workflow.
  7. Persist agent instructions: record actual commands, architecture, and conventions in the repository.
  8. Use Spec → Plan → Implement: define behavior before code and verify each implementation phase.
  9. Demand completion evidence: require passing commands and a demonstrated end-to-end result.
Compact reusable kickoff prompt Audit the environment and explain blockers before installing anything. Interview me for the product intent, users, core entities, invariants, and one small end-to-end workflow. Scaffold using the repository's established stack and conventions. Implement that workflow from persistence through API to UI. Keep business entities separate from API contracts, centralize external calls, add focused automated tests, and verify every phase with executable commands. Create concise repository instructions containing the real architecture, commands, and feature-development sequence. Do not invent missing product rules; ask me.
07 / Project fit

Does this silo you?

It strongly constrains the implementation, but the underlying method is portable. That distinction is healthy: each project should have deliberate constraints, while different project types should use different constraints.

Strong fit

  • Dealer and customer portals
  • Inspection and compliance systems
  • Internal operational tools
  • Inventory and equipment management
  • Administrative workflows
  • Rule-heavy, auditable record systems

Requires a different scaffold

  • Firmware running on a panel
  • Native mobile applications
  • Static informational sites
  • Data notebooks or command-line tools
  • Highly offline field applications
  • Embedded real-time control loops

As written, the scaffold commits you to a browser-based, API-driven business system using React, ASP.NET Core, SQL Server, containers, OIDC authentication, and separate repositories. Those are replaceable implementation decisions. The discipline of explicit requirements, boundaries, verification, and documentation is reusable everywhere.

08 / Your product world

Concrete security-panel applications

Each example starts with a user-visible outcome and follows it through the systems required to deliver and verify it. Open each example for the product rules that matter.

01Dealer backend: remote panel configuration

A dealer selects customer accounts, reviews panel compatibility, schedules a setting change, and monitors completion.

Configuration job table → entity and rules → API → dealer job list → status detail → panel command → audit history → tests

Key invariants: dealers can access only their hierarchy; unsupported firmware cannot receive the command; previous and new values are recorded; and retries cannot apply a change twice.

02Firmware OTA rollout management

The web control plane manages firmware releases, eligibility, rollout waves, pauses, and failure analysis.

Firmware release → hardware compatibility → eligibility rules → rollout wave → upgrade attempts → failure reasons

The current scaffold fits the control plane, not the firmware binary. Firmware needs its own instructions covering embedded language and toolchain, memory and timing limits, protocol compatibility, bootloader behavior, hardware tests, rollback, and recovery from interrupted upgrades.

03Dealer backend: equipment compatibility

A dealer selects a panel model and firmware version and sees compatible sensors, communicators, keypads, and feature restrictions.

Key rules: compatibility is version-specific; end-of-life devices remain visible for installed systems; blocked combinations explain why; and scheduled compatibility changes do not become active early.

04Cross-system feature: partition expansion

The shared functional specification would define maximum partitions by model, upgrade and downgrade behavior, existing sensor assignments, invalid references, command formats, panel acknowledgements, dealer-visible errors, and adoption telemetry.

The web scaffold controls dealer configuration. A separate firmware plan controls validation and storage on the panel. The API contract between them must be explicit and versioned.

05Dealer backend: walk test and sensor verification

A dealer starts a test, watches sensor activity arrive from the panel, records exceptions, and exports results.

Account equipment can be prepopulated, panel events can provide evidence, and the dealer can add observations. Required devices cannot silently disappear; reports distinguish tested, failed, skipped, and unreachable equipment.

06Dealer troubleshooting timeline

A dealer sees a normalized timeline of firmware changes, communication failures, trouble conditions, commands, and dealer actions.

The product specification must define ordering, event deduplication, permissions, retention, time zones, and which internal evidence is appropriate to expose externally.

Treat the prompt as a template, not immutable policy

The durable lesson is bigger than this particular technology stack.

Make important decisions explicit. Give humans and AI fast feedback. Prove one real workflow early. Keep behavior in durable specifications instead of chat history. That method transfers to dealer portals, backend services, firmware, integrations, and data products even when every individual technology changes.
